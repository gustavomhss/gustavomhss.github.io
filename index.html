Omni · process and terminal runtime (Rust)

Runs processes and terminals from TypeScript with the same tested behaviour on Windows, macOS and Linux. Never uses a shell; stops the whole process tree; never hangs on terminal exit.

Sourcenative/omnicratesprotocol.mdacceptance.mdconformancecore/src/omni.ts

  • Problem

    No TypeScript library contains a process tree at the kernel level; none cleans up after a host crash outside Windows; ConPTY terminals hang or lose output. A survey of 10 open-source agents counted 1,592 issues of this kind.

  • Supervisor

    Separate process started once per host; creates every child. Framed protocol over socketpair (Unix) or private named pipe (Windows); pipe ends pass by SCM_RIGHTS / DuplicateHandle, so output never flows through the supervisor.

  • Containment & host death

    Session leader on Unix (POSIX_SPAWN_SETSID) or kill-on-close Job on Windows. Supervisor watches host via pidfd / kqueue / process handle and stops the tree on host death, kill -9 included; unreaped root prevents recycled-PID signalling.

  • Terminals & limits

    Own PTY layer (openpty, TIOCSCTTY, setsid on Unix; ConPTY on Windows). Per-stream buffers with counted, ordered drops; optional RSS cap; Windows AppContainer with no network, per-path ACL grants and brokered loopback access.

  • Evidence & scale

    One JSON conformance set runs unchanged through Rust and TypeScript runners; skipped scenario = failure. Per-OS guarantees listed only with passing CI: tree stop, scope exit, host-death cleanup, I/O and PTY all green on Linux, macOS and Windows. 36k Rust lines, 271 Rust tests.

Relay · acceptance gate for agents

Runs checks outside the agent at the exact moment it stops. Moves it through an ordered plan only when controls pass; records every verdict in a tamper-evident ledger.

Sourcemodules/relaysrc/armledgerhookper-agent-arms.mdLangGrapheditor UI

  • Plan & gate

    Ordered phases of work packages, each with instructions and a checklist of named controls (shell exit-0 or advisory LLM judge, blocking if marked). On every agent stop: current controls + regression checks on earlier passing commands. Pass = reveal next package; fail = same package with named control failures.

  • Escalation

    When retry budget spends or a blocked claim repeats: run parked for a human. Release resets budget and re-runs the same gate; it never waives a control.

  • Ledger

    JSONL hash chain with HMAC-SHA256 (per-project key; SHA-256 fallback). relay verify detects added, changed or removed controls against the plan. Every hook decision records session, call, message, agent and tool as a durable event.

  • Sub-agents & concurrency

    Per-arm token pinned to the first agent_id; any different agent refused; two tokens in one transcript refused. Per-arm run lock serializes evaluation; chain lock serializes ledger append. Stale locks recovered only after recovery is written to the ledger.

  • Evidence & scale

    State-machine table covers 7 transitions (advance, complete, gate-fail, regression-fail, escalate, release, defect / busy). 12k lines Solid/TypeScript, 30 HTTP routes, Playwright end-to-end specs.

HuGR Lean · tool-output compression with exact recall

Local, deterministic filter. Keeps failures whole. Stores every original for byte-exact recall. No network calls, no extra model calls, no runtime dependencies.

Sourcegithub.com/HuGR-Leannpm: hugr-leanlean-output.tslean-recall.ts

  • Lossless pass

    Strips ANSI/OSC escapes and CR overwrites; collapses identical line runs; folds line-number prefixes; keeps exact-preserving views for grep/glob/directory listings.

  • Summaries & budget

    Shell above 4 KiB: ~1.5 KiB head + tail with omitted markers; failure blocks kept regardless of budget on nonzero/unknown exit. Reads and web fetches above 8 KiB cut at a line boundary with continuation offset.

  • Recall & safety

    Every summary ends with a recall id; original in a 64 MiB per-project store (7-day retention). lean_recall returns byte-exact. No summary without stored original; output never larger than input; errors fail open.

Atlas · deterministic codebase knowledge (OKF / architecture wiki)

Atlas is not a search result — it is a git-native, content-addressed knowledge layer. It answers "what is true about this code, and is it still true?" without embeddings or RAG. Every claim is either grounded (anchored to a structural unit pinned by a BLAKE3 blob hash) or rejected by a fail-closed gate. The system that produces, holds, updates and verifies that knowledge is structured in six layers.

What OKF means in this codebase

OKF (Orchestra Knowledge Format) is the frozen schema for every architecture claim. It is a content-addressed file format stored under docs/knowledge/ — each concept is a JSON/YAML object with: a 40-hex blob anchor (source_blobs) pointing at the exact file content hash; a checkpoint_sha (commit id, deprecated but kept for audit); the concept name (e.g. corelink-loc-cap-l210, replication-failover, launch/tier-model); the claim body (status, evidence links, invariants); and a reconcile footnote showing when the last drift was repaired. A 146-concept OKF wiki covers auth/security/tenancy/flows/storage; 14 of those are T0 structural invariants audited against real mutations.

The OKF anti-drift gate (C4 / C5 in CI) compares the blob hash of the cited source file at authoring time against the current file content. If the content changed but the claim didn't, the gate fails with [C5] STALE; if the claim was updated but the source didn't move, it passes. The gate also detects orphaned checkpoints (a commit id that no longer exists after squash/rebase) and squash-resilient blob anchors that survive any rebase. A 40-character forged blob hash paired with one cosmetic edit turns a real STALE into a fake ✅ valid — the gate's own header comment admits this explicitly; the fix is the source_blobs mechanism plus the fail-closed comparison against actual BLOB content. The OKF concepts are stored in the architecture wiki (validated in CI against the live source tree); the format itself is the contract — the file locations are secondary.

How knowledge is generated, saved, updated and consolidated

The lifecycle lives in the knowledge package (src/lifecycle/ — emit, status, reconcile, freshness, evaluator, hits) and is separate from memory. The sequence for any agent (Maestro, Jimmy, Atlas itself, or an external session) is:

  • Emit (grounded fact creation)

    A proposal enters through atlas-emit (one of two governed write doors, the other being atlas-link / sameAs). Before admission, the proposal is checked by structure proof (SCIP dump + tree-sitter tag → structural unit reference) or by LLM advisory tier (budgeted, never blocking). The grounding package enforces: a fact is served as truth only while grounded ∧ FRESH. No ground = no admission. Genesis (L8 package) runs the one-time cold-start miner: deterministic $0-LLM S0 (SCIP index + integer fixed-point PageRank over import graph) → $0-LLM S1 (budgeted proposal + two-door admission: WhyNot check + mechanical admission). The output is a seed set of grounded concepts written as OKF files.

  • Status & drift reconciliation

    The index package builds a structural index from SCIP dumps, stored as a BLAKE3 Merkle tree with three axis-views: spatial (file location), territory (scope prefix), dependency (blast radius = reverse closure). A fact's status moves through the lifecycle: FRESH (content matches anchor) → DRIFTED (content changed, claim unchanged) → BROKEN (claim conflicts with structure). The drift oracle is subtreeHash equality — never line ranges. When a PR touches a file cited by an OKF concept, the reconcile agent (post-merge hook) updates the checkpoint_sha or flags the concept STALE; the gate fails the build until repair.

  • Memory consolidation (per-seat, scoped)

    The memory package (L6) owns per-seat scoped memory, held strictly separate from Knowledge by a fail-closed partition (ADR-0003). Memory is inject-only-own: a seat can only inject memory belonging to its own agent id; reading another seat's memory requires an explicit relate() query over the dependency axes with a bounded budget. Memory writes use a Rules slab (top-12 by frecency, evict-never-delete — only supersede) and a templated write format (not free-form). The orchestrator's context continuity layer (L7 tools + L6 memory) produces the bounded pack that feeds each agent turn: a ~2K-token pack of T0 facts (highest structural rank) followed by T1 advisory facts, with an injection-ceiling drop-order (two pins never drop, stale-not-trusted). The original byte stream is stored for recall; old outputs are masked in the request copy but never changed.

  • Knowledge retrieval (bounded assembly)

    The retrieval package builds the bounded pack deterministically: relate() over the axes, then own_<unit> filtering (only facts whose scope matches the agent's seat). The pack has a ceiling: two pins (the two highest-rank structural facts for the session's domain) are never dropped; everything else is ranked by structural relevance and cut at the budget. A stale concept is downgraded to advisory; a broken concept is excluded. The retrieval surface exposes three governed tools (atlas-query, atlas-emit, atlas-link) plus the read-only doctor (atlas-diff, atlas-projection).

How the context algebra works in practice

The context algebra (registry + built-ins in packages/core/src/system-context) defines what a session's working memory is: a versioned, seven-section record with host-assigned ids (stable aliases like u7, a12, t41), a content-addressed archive verified on read, and a five-mode context_recall (full, compact, archive, etc.). When the session hits 40% of the context window, background maintenance forks; at 70%, it is forced. The continuity layer masks old tool outputs in the request copy but keeps the original in the archive for byte-exact replay.

For skills: each agent seat (backend, jimmy, archie, lucy, patty) carries a skill charter — a read-only or execution-bound contract that defines which OKF concepts the agent may emit, which memory it may inject, and which tools it may invoke. The backend specialist carries 21 pinned codegen/check engines (sqlc, buf, protoc-gen-es, openapi-generator, sqlx, gitleaks, squawk…) with 6 skills and 68 references across 8 protocols, 5 languages, 4 libraries; each engine fetch is pinned by SRI or lockfile integrity. The Jimmy research seat holds the SCIP + tree-sitter index (SQLite FTS5) and performs no LLM calls for the read path — only deterministic reciprocal-rank fusion (k=60) plus a PageRank bonus over the import graph. The Archie planning seat writes only complete, versioned sprint cards with the five card axioms (Completeness Criteria, Success Criteria, Invariants, Quality Standards, Definition of Done); child cards cite the parent and write only deltas.

Format: from source to ground

The OKF concept file structure (as used in the architecture wiki and validated by the C4/C5 gates) is:

OKF concept format (simplified)
concept: replication-failover
checkpoint_sha: a7c7cfb6... (optional)
source_blobs: ["routes/dsr/access.rs@e4b3...", ...]
status: FRESH | DRIFTED | BROKEN
scope: <path-prefix>
evidence: [URL | sha | description]
invariants: [<named-constraint>]
ratify: INIT | TIER | FASTPATH
reconcile_note: <date + diff-summary>

A reconcile note records the date of the last repair, the diff summary, and whether the repair changed meaning or only shifted line numbers. The gate C5 compares the current file content to the blob hash; if they differ and the reconcile note does not explain the shift, the concept is STALE and the build fails. The gate C4 checks that every OKF-cited file has its checkpoint_sha present in the git object database; a squash-merge that removes the commit produces an orphan, which is caught by the same gate. The anti-drift mechanism uses blob hashes for squash-resilience and commit hashes for audit history; both are stored so a future auditor can reconstruct either axis.

How skills are built and bound

Skills are not prompts — they are charter-bound contracts stored under modules/specialists/<seat>/. A skill file names: the allowed input (what OKF concepts the agent may read), the allowed output (what concept types it may emit — proposal, assumption, observed source, blocker, or owner decision), and the forbidden surfaces (e.g. review seats have no shell; execution seats cannot run git push, open PRs, or release). The Charlie backend specialist receives a packet from Maestro (behaviour, acceptance criteria, exact write paths, checks) and returns a closed backend-result card. It may not diagnose, decide architecture, delegate, self-review, claim acceptance, or run git; writes are restricted to host-owned paths; symlink-safe edits are enforced. Each claim in the result card is labelled with one of six types (fact, observed_source, proposal, assumption, owner_decision, blocker); missing data stays UNKNOWN, never an empty pass.

Integration with Orchestra: Atlas is consumed by the Orchestra desktop app and CLI through three agent tools (atlas-query, atlas-emit, atlas-link) and a bounded retrieval layer. The app's session runner loads the session's working memory from the retrieval package (bounded ~2K-token pack) before every provider turn; after compaction, the original is preserved in the content-addressed archive for byte-exact replay. The context continuity module (L7 tools + L6 memory) co-locates continuity hooks (PostCompact, SessionStart(compact)) with the memory registry so the continuity layer never takes a raw Session ID — only structured context. Atlas never imports Orchestra; Orchestra consumes Atlas through its governed surface.

How I work — in practice

Not a checklist. Four operating patterns that show up in every project above: design by contract, verify before claiming, never review yourself, and ship the proof with the code.

Design by contract

Before any implementation, the wire format, null behaviour, and error cases are frozen as text in the repo. In Omni, the protocol doc (SCM_RIGHTS / DuplicateHandle, session leader semantics, unreaped-root rule) was written before the supervisor crate; the Rust code follows the doc, not the other way. In Relay, the state-machine table (7 transitions, escalation rules, regression budget) defines what the code must do; the 30 HTTP routes and 12k TypeScript UI lines implement that table exactly. Changes to the contract force a visible diff; changes to the code that do not touch the contract are invisible to consumers.

Verify before claiming

Every claim in the portfolio above is paired with a check that can fail independently of me. Atlas: 23,702 planted mutations run through the same indexer; a single false admission fails the build. Lean: live A/B on 8 pinned tasks (protocol fixed before the run) measures −47.9% input; if task success had dropped, the claim would be retracted. Omni: 45 JSON conformance scenarios count a skipped scenario as failure; green on Linux/macOS/Windows is required before any per-OS guarantee appears in docs.

Never review yourself

The Maestro governance chain separates planning (Archie), execution (backend/Charlie), and review (Lucy / Billy / Frank). A review seat has zero shell or edit access; an execution seat cannot push, open PRs, or release. .env is unreadable to every seat. The cold review reads the verbatim demand, not my summary; the host verifies authorship from original bytes before appending package verification. This is not process theatre — it is how I catch my own errors without relying on memory.

Ship the proof

Every deliverable includes the evidence that validates it. Relay: the ledger (JSONL HMAC-SHA256 chain) records every control verdict; relay verify detects added or removed controls. Lean: 2,715 fixtures replay 343,045 real tool calls; the original byte stream is stored with every summary, recallable by id. Omni: CI runs the same 45 scenarios unchanged through Rust and TypeScript runners; conformance passes on all three OSes are listed only with the passing CI link. The claim and its falsifier travel together.
