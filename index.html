Omni · process and terminal runtime (Rust)

Runs processes and terminals from TypeScript (Node, Bun, Deno) with the same tested behaviour on Windows, macOS and Linux. Built for AI agents and developer tools: resolves commands the same way on every OS, never uses a shell, stops the whole process tree, and never hangs on a terminal exit.

Sourcenative/omninative/omni/cratesprotocol.mdacceptance.mdnative/omni/conformancecore/src/omni.ts

  • Problem

    No TypeScript library contains a process tree at the kernel level, none cleans up after a host crash outside Windows, and ConPTY terminals hang or lose output. A survey of 10 open-source agents counted 1,592 issues of this kind.

  • Supervisoromni-supervisor

    A separate process, started once per host, creates every child. The host never forks and installs no signal handlers. Framed protocol over a socketpair (Unix) or private named pipe (Windows); pipe ends pass by SCM_RIGHTS or DuplicateHandle, so output never flows through the supervisor.

  • Containment

    Each root is a session leader on Unix (POSIX_SPAWN_SETSID; stop signals the whole session) or lives inside a kill-on-close Job on Windows that children cannot leave. The root stays unreaped until its session is empty, so a recycled PID is never signalled.

  • Host death

    The supervisor watches the host through pidfd, kqueue or a process handle and stops every tree when it dies, kill -9 included.

  • Terminals

    Own PTY layer: openpty, setsid and TIOCSCTTY on Unix; ConPTY on Windows. Start is gated so fast-exiting programs lose no output; ClosePseudoConsole runs under its own deadline.

  • Output & limits

    Per-stream buffers; dropped bytes counted and reported in order; the child never blocks on output. Optional RSS cap on the whole tree. Windows AppContainer sandbox with no network, per-path ACL grants and brokered access to exact local ports.

  • Evidenceconformance

    One set of JSON conformance scenarios runs unchanged through the Rust and TypeScript runners; a skipped scenario counts as a failure. A per-OS guarantee is listed only with a passing CI run: tree stop, scope exit, host-death cleanup, I/O and PTY are green on Linux, macOS and Windows.

  • Scale

    36k lines of Rust in 4 crates (core, supervisor, protocol, fixture) plus a napi binding; 271 Rust tests; 45 conformance scenarios. On by default in Orchestra: Effect spawner, shell tool, PTYs, MCP stdio servers, background jobs and the Windows sandbox.

Relay · acceptance gate for agents

Runs acceptance checks outside the agent at the moment it stops, moves it through an ordered plan only when they pass, and records every verdict in a tamper-evident ledger.

Sourcemodules/relaysrc/armsrc/ledgersrc/hookper-agent-arms.mdLangGraph (Python)editor UI

  • Plan

    A sprint is an ordered list of work packages grouped into phases. Each package has instructions and a checklist of named controls, its definition of done. Controls are shell commands (exit 0 passes) or an LLM judge, advisory unless marked blocking.

  • On every stop

    Runs the current package's checks and re-runs earlier passing commands to catch regressions. A pass hands the agent the next package; a fail blocks it on the same package with the failing control names.

  • Escalation

    When the retry budget runs out, or the agent repeats a claim already blocked, the run is parked for a human. The release resets the budget and re-runs the same gate; it never waives a control.

  • Ledgerchain.ts

    JSONL hash chain, HMAC-SHA256 under a per-project key (SHA-256 fallback), recording a hash of each control. relay verify checks integrity and detects controls added, changed or removed against the plan.

  • Runtime hooksevaluate.ts

    Small graphs on agent tool calls or on session start, prompt and idle: block, ask for approval, run a sandboxed check with pass/fail branches, demand repair, remind, record. Hooks only restrict, never grant, and apply to Orchestra and Claude Code tools; every decision is a durable event.

  • Workflowsrelay-workflow-binding.ts

    Linear phase/step workflows on a canvas, published as immutable versions. A Maestro plan binds a published workflow; the host appends package verification and an independent code review on the exact working tree. A missing binding holds the run, never passes it. Each run gets a receipt with per-step verdicts.

  • LangGraph__init__.py

    gated(builder, {...}) adds check and approval nodes around chosen nodes of an existing graph and rewires their edges with bounded retries. Approval runs through interrupt() and is never asked twice. Runs write a verifiable ledger shown in Orchestra as external runs.

  • State machinestate.ts

    Each run is an arm: plan, position (<phase>.<wp>), per-package retry and regression counters, ledger. Live states active, awaiting-human, complete; every stop drives exactly one transition.

    • Claude Code subagents: the orchestrator puts an arm token in each subagent's prompt; the SubagentStop hook reads it from that subagent's own transcript. The first stop pins the arm to its agent_id; any other agent is refused; a transcript naming two tokens is refused, not guessed; tokenless stops are ignored.
    • Orchestra child sessions: Maestro derives the child session from the dispatch authorization, creates the arm with that session as its only agent and records WorkflowBound.     • Concurrency: a per-arm run lock serializes evaluation (a second stop gets busy); a chain lock serializes ledger appends; a stale lock is recovered only after the recovery is written to the ledger.
    • Hook attribution: every hook decision records session, call, message, agent and tool, as a durable event and an idempotent ledger line.

HuGR Lean · tool-output compression with exact recall

Local, deterministic filter for coding-agent tool output. Summarizes large shell, read and web-fetch results before the model sees them, keeps failures whole, and stores every original for byte-exact recall. No network calls, no extra model calls, no runtime dependencies. Published on npm as hugr-lean with provenance; runs as a CLI, a library and an agent plugin.

Sourcegithub.com/gustavomhss/HuGR-Leannpm: hugr-leanorchestra/session/lean-output.tstool/lean-recall.ts

  • Problem

    Tool output re-enters the context and is re-read as cached prefix on every later call; large logs, file dumps and pages dominate an agent loop's input cost.

  • Lossless pass

    Strips ANSI/OSC escapes and carriage-return overwrites, collapses runs of identical lines when that saves bytes, folds line-number prefixes into one header, and keeps exact-preserving views for grep, glob and directory listings.

  • Summaries

    Shell output above 4 KiB keeps about 1.5 KiB of head and tail, marks omitted lines, and keeps failure blocks (the matching line plus its stack or continuation lines); on a nonzero or unknown exit every failure block is kept regardless of budget. Reads and web fetches above 8 KiB are cut at a line boundary with a continuation offset.

  • Recall & safety

    Every summary ends with a recall id; the original sits in a per-project store (64 MiB, 7-day retention) and lean_recall returns it byte-exact, with an optional line range. No summary without a stored original; output never larger than input; internal errors fail open; error results, attachments, binary output and unknown tools pass through.

  • Profiles

    20 built-in tool profiles: Cargo, pytest, Go, Node TAP, tsc, ESLint and Biome, Ruff, Pyright, Pylint, git status, ripgrep and others.

  • In Orchestra

    Pinned as a byte-identical, attested tarball; runs after execution and policy on shell, read, fetch, glob and grep results. Never rewrites commands, permissions, exit status or lifecycle, only the text the model sees. Each decision is persisted once so replay reuses it; the research specialist gets no lossy summaries. Per-profile toggles, HTTP API and a telemetry dashboard in the desktop app.

    6.6k lines of TypeScript source, 23k lines of tests (about 950 cases), 2,715 fixtures, CI on Linux, macOS and Windows, three releases up to 0.4.0.

Atlas · deterministic codebase knowledge

Answers "what is true about this code, and is it still true?" without embeddings or RAG. Orchestra consumes Atlas; Atlas never imports Orchestra.

Sourcemodules/atlasARCHITECTURE.mdBENCHMARKS.mdpackages

  • Index

    Grounded facts pinned to source@sha. Structural index built from SCIP dumps and stored as a BLAKE3 Merkle tree with spatial, territory and dependency axes. Blast radius is the reverse closure of the dependency graph.

  • Drift

    Subtree hashes, not line ranges. A fact moves FRESH → DRIFTED → BROKEN; the gate admits only grounded, FRESH facts and fails closed. Facts proven from structure cost no LLM calls; a rationed LLM tier proposes advisory facts.

  • Ownership

    A policy maps scopes to the actors allowed to write them; path prefixes bind to scopes and the most specific wins. Mismatched writes are refused, no policy means no writes, reads are never gated. Memory is per agent seat; an unowned write throws.

  • Interfaces

    CLI (32 commands) and MCP server (18 tools) return the same verdict for the same input. Inside Orchestra: three agent tools, a per-turn header and checkpoint restore after compaction.

  • Benchmarks

    0 false admissions across 23,702 planted dependency mutations and 163/163 recall against a tsc oracle (on Atlas itself). 231 dependency edges on zod versus 129 for madge, every madge edge included. Advisory-fact precision 93.8% on Atlas, 86.8% on zod (LLM panel).

  • Scale

    15 packages, 49k source lines, 89k test lines (3,586 tests), 706 requirements, 1,075 scenarios, 13 architecture and spec guards in CI.

Maestro and the specialists

Maestro routes work and never implements, approves or reviews its own work. Governed chain: admission → plan revision → context → validation → cold review → owner approval → authorization → execution → result decision. Records are write-once; approvals are bound to five hashes. Deny-by-default profiles: review seats have no shell or edit, execution seats cannot push, open PRs or release, .env is unreadable. 29 Orchestra-specific agent tools, a 26-capability planning arsenal and 19 shipped skills.

Context continuity

  • Continuity

    Background maintenance from 40% of the context window, forced at 70%. A fork that keeps the prompt cache valid updates a versioned seven-section working memory with host-assigned ids. Per-session content-addressed archive, verified on read. Old tool outputs are masked in the request copy; stored history never changes. Stable u7/a12/t41 aliases and a five-mode context_recall.
